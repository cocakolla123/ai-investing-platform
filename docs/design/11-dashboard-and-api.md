# 11 — Dashboard & API

The dashboard is the single user's window into the platform and the only place admin actions
happen. It is **read-heavy by design**: the platform runs unattended; the human reviews,
approves, and occasionally intervenes. Grafana owns ops/system views (`12-operations.md`); the
app dashboard owns **investment views only** — no metric is rendered in both places.

## 1. API surface (FastAPI)

One stateless `api` container (doc 01 §3), Uvicorn, OpenAPI schema auto-generated and committed
as a snapshot (`docs/api/openapi.json`, regenerated by `make openapi`, diffed in CI so surface
changes are visible in review). All response models are pydantic and **reuse domain entities
directly** (`CommitteeVerdict`, `RiskVerdict`, `Position`, `JournalEntry`, …) wrapped in thin
envelope models (`Page[T]`, `AsOf[T]`) — no parallel DTO hierarchy to drift out of sync.

### 1.1 Read endpoints

| Endpoint | Returns | Notes |

### 1.2 Admin actions (the complete list)

Admin actions are deliberately few — every one corresponds to a human-in-the-loop boundary from
doc 00 §8. Each is idempotent, audited (`admin_actions` table: who=owner, what, when, payload),
and returns the new state.

| Endpoint | Action |
|---|---|
| `POST /universe/queue/{id}/approve` \| `/reject` | Universe-change recommendation (writes `approved_by`) |
| `POST /rebalance/{id}/approve` \| `/reject` | Rebalance proposal (doc 07) |
| `POST /improvements/{id}/approve` \| `/reject` | Improvement proposal → promotion pipeline (doc 10) |
| `POST /alerts/{id}/ack` | Acknowledge an alert (see §4) |
| `POST /killswitch` | Toggle kill-switch (creates/removes the kill-switch file, doc 01 §5) |

No endpoint mutates positions, orders, models, or config directly. There is no "edit verdict"
and no "manual trade" endpoint — manual intervention happens at the broker, and reconciliation
(doc 09) surfaces the divergence.

### 1.3 Conventions

- **Envelopes:** list endpoints return `Page[T]` (`items`, `next_cursor`, `total`); cursor
  pagination (keyset on `(as_of, id)`), default page size 50, max 500. Point reads return
  `AsOf[T]` (`data`, `as_of`, `data_cutoff`) — the as-of discipline of doc 01 §6 is visible in
  every response, so the UI can always say *when* a number was true.
- **Errors:** RFC 9457 problem+json; typed provider exceptions map to stable `type` URIs;
  no stack traces ever cross the API boundary.
- **Time:** all timestamps UTC ISO-8601 in responses; the dashboard localizes to ET for
  display (market-calendar logic stays server-side, doc 01 §6).
- **Caching:** read endpoints send `ETag` derived from the underlying as-of timestamp; the
  data changes at most nightly plus 15-minute risk checks, so conditional GETs make polling
  nearly free.
- **Versioning:** none. Single user, single deployed client, API and dashboard ship from the
  same repo and deploy together — an `/v1/` prefix would be ceremony (doc 00 §8.4).

### 1.4 Auth & exposure

Single user, per doc 01 §7: API and dashboard bind to `127.0.0.1` and are reached over
tailscale (preferred) or SSH tunnel; HTTP Basic auth (single credential from env, constant-time
compare) as defense-in-depth on top. No OAuth, no sessions, no user table. `POST /killswitch`
and approval endpoints additionally require a confirmation header (`X-Dynamo-Confirm: <action>`)
so a stray click or CSRF-ish accident can't approve anything.

## 2. Two-phase dashboard

Per the milestone plan: don't invest in frontend polish before there is anything worth looking
at, but don't let a throwaway UI ossify into the product either.

| Phase | Stack | Role |
|---|---|---|
| M1–M5 | **Streamlit** | Disposable working UI. May call the API *or* read repositories directly (it runs in the same trust boundary); zero design effort; every screen in §3 exists here in rough form |
| M6+ | **React + Vite + TypeScript**, shadcn/ui, TradingView `lightweight-charts`, TanStack Query | The real dashboard. Talks **only** to the API (this forces the API to be complete before Streamlit is deleted); served by nginx in the `dashboard` container |

Rules for the transition:
- The Streamlit app is deleted at M6, not maintained in parallel. Its screens are the
  acceptance checklist for the React app.
- Any repository-direct read the Streamlit app used must have gained an API endpoint before
  M6 — the API surface in §1 is the contract, discovered early and cheaply.
- TanStack Query polls; no WebSockets. The data changes nightly and every 15 minutes at most
  (intraday risk checks); polling at 60s is sufficient and boring (doc 00 §8.4).

## 3. Screen inventory

Eight screens. Each lists its contents; anything not listed is not on the screen.

### 3.1 Overview

- Equity curve vs SPY total return (paper account), selectable window
- Allocation donut (sleeve → sector), cash % prominent
- Regime badge (`risk_on`/`neutral`/`risk_off`/`crisis`) with the composite score inputs on hover
- Drawdown ladder state (current rung, distance to next trigger, hysteresis status)
- Abstention rate (rolling 30d) — displayed as a *health* indicator, per doc 00 §4
- Alert strip: unacked alerts, severity-colored, ack inline

### 3.2 Positions

- Open positions table: entry date/price, current stop (type: ATR/trailing/thesis/disaster),
  unrealized P&L, weight vs cap, risk contribution (% of portfolio vol)
- Each row links to the entry `DecisionContext` snapshot and the originating
  `CommitteeVerdict` — the "why do I own this" click is one hop, always
- Pending exit-review flags (time stops, thesis-stop predicate hits)

### 3.3 Research

- Ranked watchlist: committee action + conviction, quant score, `quant_alignment`,
  disagreement score, staleness
- Committee report view per symbol: full thesis, bull case, bear case, **dissents and
  self-critique rendered always** (never collapsed away — doc 03 §2), evidence references
  resolvable to source records, disagreement breakdown (doc 03 §4)
- Dossier browser: analyst fact base + event-specialist entries, filing deltas, data gaps
- **Deep-dive request button**: queues a symbol for the next nightly deep-dive set (counts
  against the nightly cap, doc 03 §1; the button says so)

### 3.4 Risk

- Limit utilization bars: per-position, sector, cluster, gross, cash floor, VaR — current vs
  Medium-preset cap vs hard bound (doc 06 §2)
- VaR/CVaR (95/99), VaR-exception traffic light (Kupiec state, doc 06 §6)
- Deterministic stress results table (scenario → equity impact → ladder implication)
- Correlation cluster view: cluster membership, cluster weight vs 30% cap
- Monte Carlo fan chart: 20d equity paths, P(ladder trigger) per rung

### 3.5 Performance & attribution

- Attribution: per-sleeve, per-strategy, per-sector; turnover; realized slippage vs model
- Calibration curves per agent and for the committee (reliability diagrams + Brier trend,
  doc 10) — the primary "is the AI trustworthy" view
- Strategy performance vs backtest expectation bands (doc 08): the realized (paper) path drawn over the
  backtest confidence envelope; excursions flagged

### 3.6 Journal

- Full-text + semantic search (pgvector) over journal entries with filters (symbol, tag,
  outcome, date)
- Similar-situations explorer: given a current verdict or position, nearest historical
  situations with their outcomes — the same retrieval the arbiter consumes (doc 03 §1)

### 3.7 Prediction markets

- Tracked markets passing the thin-market filter: question, venue, market-implied vs
  committee-estimated probability, edge, confidence, resolution date
- **Uncertainty framing is mandatory UI copy**: `uncertainties` and `why_wrong` lists rendered
  with the estimate, never behind a click; thin-market `untrusted` flags shown
- Banner on the screen, verbatim: *"Research only. No execution hooks exist."* (doc 00 §7,
  doc 03 §6)
- Calibration: implied vs estimated tracked over resolved markets

### 3.8 Ops-lite

Investment-adjacent operations the owner acts on (full ops live in Grafana):

- Pipeline run status: last nightly run, per-stage results, quarantined LLM calls
- Claude spend vs `CLAUDE_MONTHLY_BUDGET_USD` from `cost_meter` (gauge + month projection)
- Data-quality quarantine list with reasons and suppressed-signal notices (doc 02 §6)
- Universe-change queue and improvement-proposal queue with approve/reject (the §1.2 actions)

## 4. Alerts on the dashboard

The alert catalog, severities, and delivery (Telegram) are owned by `12-operations.md`. The
dashboard's role: every alert is listed with its catalog entry, and **ackable alerts can be
acked here** (`POST /alerts/{id}/ack`). Ackable: warn/info-class alerts (budget 70%, quarantine
counts, ladder −5%). Not ackable from the UI: page-class alerts that demand an action elsewhere
(kill-switch state, reconciliation divergence, backup failure) — these clear only when the
underlying condition clears, preventing "ack and forget" on things that matter.

## 5. Testing

| Layer | Approach |
|---|---|
| API contract | Schemathesis against the OpenAPI snapshot + explicit tests per endpoint (status codes, envelope shape, auth required, confirm-header enforcement on admin actions) |
| Response models | Round-trip tests: repository fixtures → endpoint → pydantic validation of documented model (catches domain-model drift immediately, since responses reuse domain models) |
| Report rendering | Snapshot tests: frozen `CommitteeVerdict`/report fixtures → rendered output compared to golden files; dissents/self-critique presence asserted (a render that drops dissents is a failing test, not a style choice) |
| Admin actions | Idempotency + audit-row tests; kill-switch toggle round-trip in TEST env |
| Dashboard (M6) | Playwright smoke: each §3 screen loads against a seeded TEST database; no per-pixel testing |
